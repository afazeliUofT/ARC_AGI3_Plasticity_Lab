## 2. `protect_control_surface.sh` does not match absolute paths (not blocking, but real)

Line 6 of the hook:

```
protected='(^|[^A-Za-z0-9_./-])(preregistration/|scripts/verify_run\.py|...|\.claude/|docs/EVIDENCE_)'
```

The negated class excludes `/`, so a path whose protected segment is preceded by `/` never
matches. The Write and Edit tools always send absolute paths
(`/home/afazeli2006/ARC_AGI3_Plasticity_Lab/preregistration/G0.yaml`), so layer 1 of controls
C1/C2 does not intercept them. Bash commands with absolute paths pass too. Only relative paths
in Bash are caught. I did not demonstrate this empirically because the demonstration would be
a write into the control surface. You can confirm it in one line:

```
printf '/x/preregistration/G0.yaml' | grep -qE '(^|[^A-Za-z0-9_./-])(preregistration/)' ; echo $?   # prints 1 = no match
```

Suggested fix: `(^|/|[^A-Za-z0-9_.-])`. Also, the `writes` pattern matches any `>` including
`2>&1`, which denied a read-only `ls -la .claude/settings.local.json 2>&1`; harmless but noisy.

Layer 2 (the supervisor's pinned hashes) covers only the six files in `CONTROL_SURFACE`; it does
not pin `preregistration/**` or `docs/EVIDENCE_*.md`. Consider pinning a pre-registration's hash
once its gate has an artifact, so C1 holds even if the hook is bypassed.
